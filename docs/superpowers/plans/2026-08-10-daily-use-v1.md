# Daily-use V1 implementation plan

**Goal:** Make Artha reliable for everyday personal and shared-money tracking,
while keeping real financial text away from unpaid AI services.

**Safety boundary:** Every financial write is server-owned, atomic, idempotent
and auditable. AI may propose a draft or render grounded read-only insights; it
cannot write to the ledger. Money remains integer paise and every capture still
requires explicit confirmation.

## Senior product audit translated into this release

| Product gap | Release response | Status |
| --- | --- | --- |
| Search covered only recent rows | Search all owner activity in Postgres and return a bounded relevant result set | Implemented; release verification pending |
| Accounts/cards could not be maintained after onboarding | Add/edit/archive/restore and audited balance reconciliation | Already deployed |
| A saved transaction was a dead end | Add **View transaction** after confirmation and open any history row | Implemented; release verification pending |
| Mistakes could not be corrected safely | Atomic void-and-replacement correction with a required reason and audit trail | Implemented; release verification pending |
| Duplicates could not be removed from totals | Pair-safe logical void with a required reason and idempotent replay | Implemented; release verification pending |
| Shared balances had no repayment loop | Record an existing participant's repayment without counting it as income/spending | Implemented; release verification pending |
| AI disclosure was too long and looked like a pilot | Show one concise privacy status; keep technical/provider details collapsed | Implemented; release verification pending |
| Mobile dialogs needed release-grade keyboard behavior | Focus entry, Escape close, focus trap, scroll lock and focus restoration | Implemented; release verification pending |

This sprint deliberately does not add invitations, autonomous financial
actions, investment tracking, bank aggregation, WhatsApp, OCR, budgets or
financial advice.

## Delivery tasks

### 1. Production trust evidence

- [x] Run the rollback-only two-household isolation contract against the exact
  Artha production project.
- [x] Run the rollback-only encrypted recovery round trip against the exact
  Artha production project.
- [x] Record sanitized evidence without identities, balances or credentials.

### 2. Atomic transaction correction and removal

- [x] Add `replace_transaction` with canonical request hashing, exact replay,
  deterministic account locks, pair-safe transfer replacement and one audit
  event.
- [x] Add `void_ledger_activity` so one logical transfer is removed as a pair.
- [x] Add PATCH/DELETE production routes with reviewed payloads, reasons and
  idempotency keys.
- [x] Add rollback-only SQL behavior for expense/transfer correction, removal,
  replay/conflict, audit events, balances and settlement.
- [x] Return the database-confirmed replacement ID with the reviewed replacement
  fields, avoiding an unstable history reload after the write.

### 3. Daily transaction workflow

- [x] Add **View transaction** after Quick Add confirmation.
- [x] Open history rows into an accessible detail dialog.
- [x] Allow reviewed edits to amount, description, account movement, category,
  date, note and splits.
- [x] Require a reason before correction or removal.
- [x] Refresh canonical dashboard, history and capture context after writes.
- [x] Preserve form values and show an actionable error when a write fails.

### 4. Complete-ledger search

- [x] Keep each history response bounded to 200 logical activities and expose
  **Load older activity** through a stable `(occurred_at, created_at, id)`
  keyset cursor.
- [x] Search description, category, note and either transfer account across the
  complete owner ledger inside Postgres.
- [x] Debounce search, preserve current results while loading and announce
  progress/errors accessibly.
- [x] Return at most the first 200 relevant search matches; keep type and account
  filters local over that bounded result set.

Search is intentionally bounded; normal history browsing has no fixed row cap.

### 5. Shared repayment loop

- [x] Include posted settlements in participant balances but exclude them from
  income and spending.
- [x] Derive payer/payee direction and the remaining balance inside one database
  command.
- [x] Prevent zero/concurrent over-settlement and replay the exact stored
  response before mutable balance checks.
- [x] Add a repayment dialog with account, date, amount, note and clear cash-flow
  language.
- [x] Refresh canonical balances after confirmation.

### 6. Release gate

- [x] Run the fresh full local gate, documentation links and diff checks.
- [x] Execute the daily-use SQL contract from a freshly reset database.
- [x] Complete mobile/desktop, light/dark and keyboard Browser QA.
- [x] Receive independent release review with no Critical/Important findings.
- [ ] Commit, publish a PR, pass CI/CodeQL and merge to `main`.
- [ ] Apply the versioned migration only to the exact production project and
  run rollback-safe production verification.
- [ ] Verify exact-SHA web/API deployments and signed-in final-domain behavior.

## Real-data boundary

Isolation and encrypted-recovery database contracts now pass. The remaining
real-data condition is AI privacy: production stays `sample_only` until the
Gemini Cloud project is on paid-service data terms and the owner explicitly
approves private-data AI. Manual entry remains the private path meanwhile.
